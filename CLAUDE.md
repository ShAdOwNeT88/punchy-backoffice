# Punchy back office — agent instructions

Angular 22.2 SPA (standalone components, signals, zoneless), Angular Material 22, Transloco,
Vitest. Locales: `it` (default) and `en`. Deployed as static assets on Cloudflare.

The project follows the Seshat house Angular architecture (`seshat-angular` plugin:
`angular-architecture`, `ng-review`). Declared choices and deviations are in `docs/DECISIONS.md`.

## Rules that are easy to miss

- Features never import each other, siblings included; navigate by URL. A feature may import its
  own domain's `data-access` (`features/admin/data-access`, `features/manager/data-access`),
  `@shared/*` and `@core/*`. `npm run lint` enforces this.
- `core/` imports only `core/`. `shared/` never imports a feature.
- HTTP clients are generated by orval from the committed `openapi/punchy.yaml`
  (`npm run api:generate`). Never edit `**/api/endpoints/**` or `**/api/model/**` by hand.
- Every API call goes through the generated clients; until the backend exists the mock in
  `src/mocks/` answers them (`useMockApi` in `src/environments/`). A new endpoint means: OpenAPI
  first, then the mock handler, then the client.
- No user-facing string literals: add keys to `public/i18n/<scope>/it.json` and `en.json` (or the
  global `public/i18n/it.json` / `en.json` for shared labels and enums).
- No hex colours or raw lengths outside `src/styles/`; use the `--app-*` custom properties.
- One form strategy: reactive forms.
- Business names, rewards and template names are content, never translation keys. Never
  special-case a category or a business in behaviour.

## Run and check

```bash
npm start
npm run lint
npm run test:coverage
npm run build
```

## Documentation

Durable documentation lives in `docs/`:

- `REQUIREMENTS.md` — current functional contract. `TECHNICAL.md` — current implementation.
  Both describe the system as it is now, never as a changelog.
- `DECISIONS.md` — dated decision log. Supersede entries; never rewrite them.
- `specs/` and `plans/` — historical design and implementation artifacts. Do not edit them.

After a verified change, update `REQUIREMENTS.md` and `TECHNICAL.md` in place, replacing obsolete
statements, and record durable choices in `DECISIONS.md`.
